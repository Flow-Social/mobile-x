# Decisions (ADR) — Архитектурные решения

## ADR-001: Нативный хостинг сервисов вместо Docker на сервере 31.77.9.57
- **Контекст**: Сервер имеет ограниченный объем RAM (4GB) и на нем уже запущен боевой проект `prostranstvo` (PM2, Node.js, Postgres).
- **Решение**: Flow бэкенд запускается как нативный бинарник через `systemd`, админка — через `PM2`. Никакого оверхеда Docker, мгновенный рестарт, минимум потребления памяти (~15-25 MB).

## ADR-002: Защищенный конфиг Nginx в conf.d
- **Контекст**: Деплой-скрипты стороннего проекта перезаписывали `/etc/nginx/sites-available/default` и ломали SSL и роуты Flow.
- **Решение**: Все правила Flow вынесены в `/etc/nginx/conf.d/flow.conf`. Файлы в `conf.d/` автоматически инклудятся Nginx и защищены от сторонних перезаписей.

## ADR-003: Домен nip.io для работы Let's Encrypt SSL
- **Контекст**: Для работы Android приложения (Ktor) и Google OAuth требуется валидный HTTPS с доверенным сертификатом.
- **Решение**: Использован динамический wildcard-домен `31.77.9.57.nip.io` с официальным Let's Encrypt сертификатом.

## ADR-004: Изоляция базы данных flow_db
- **Контекст**: На одном экземпляре PostgreSQL крутятся две базы: `prostranstvo_db` и `flow_db`.
- **Решение**: Пользователь `flow_user` имеет права строго на `flow_db`. Никаких пересечений с чужой базой.

## ADR-005: Корневой оверлей Compose вместо Android Dialog для полноэкранного вьюера
- **Контекст**: Использование Android `Dialog` (`DialogWrapper` / отдельный `PhoneWindow`) для полноэкранного просмотра фото вызывало задержку создания окна в 1-2 VSYNC-кадра (16-33 мс), из-за чего скрытие исходной карточки приводило к миганию («черная дыра» до первого кадра диалога), а уничтожение окна диалога при выходе вызывало рассинхрон кадров.
- **Решение**: По образцу Telegram вьюер переведен на рендеринг в том же окне/Surface на уровне корневого Compose-контейнера (`FlowNavHost.kt` с `zIndex(100f)`). Это сделало появление и исчезновение вьюера строго атомарным с исходным экраном в пределах одного VSYNC-кадра, исключило мерцания и позволило плавно затухать фону от текущей альфы жеста.

## ADR-006: Изоляция окон и локальный хостинг полноэкранного вьюера внутри диалога стопки ленты
- **Контекст**: В ленте (`SharedFeedScreen`) карточки постов раскрываются в 3D-стопку внутри отдельного окна `FeedOverlayDialogHost` (для перекрытия нижнего `FlowBottomBar`). Когда глобальный вьюер был перенесен в корневое окно `MainActivity`, клик по карточке стопки открывал вьюер в окне `MainActivity`, в то время как окно `Dialog` стопки продолжало висеть поверх него в SurfaceFlinger, закрывая TopBar и перехватывая тачи.
- **Решение**: Вьюер ленты смонтирован локально внутри самого `FeedOverlayDialogHost` с `zIndex(100f)`. Это устранило меж-оконное наложение, гарантировало совпадение координат `origin.boundsInWindow()`, корректный двухэтапный BackHandler (закрытие вьюера -> закрытие стопки) и скрытие подсказки «нажмите чтобы закрыть» во время просмотра фото.

## ADR-007: Комплексная стабилизация системы по методологии Ponytail
- **Контекст**: В результате глубокого аудита выявлены узкие места в ленте (O(N) пересчет свайпов), S3 пресайнах (отсутствие SigV4 привязки заголовков), вебсокетах (зависание лимитов соединений), видеокружках (прямоугольная компрессия) и безопасности админки/JWT.
- **Решение**: Применены минимальные точечные решения без ввода новых внешних зависимостей или лишних слоев:
  1. *Feed Undo*: откат дельт интересов за $O(1)$ (`rollbackBaseDeltas`) вместо пересчета всей истории свайпов юзера.
  2. *Feed Streak*: сканирование вперед в корзине без сброса непросмотренных кандидатов, гарантирующее разнообразие категорий и детерминированность.
  3. *S3 Security*: включение `ContentType` в подпись SigV4 для PUT-пресайна + ограничение размера входящего потока через `io.LimitReader` на бэкенде.
  4. *Auth & JWT*: сокращение TTL токенов до 60 дней, добавление `token_version` в базу и Claims с эндпоинтом `POST /api/v1/auth/logout`.
  5. *Realtime WS*: вытеснение старейшего подключения (FIFO) в `SubscribeWithLimit` вместо постоянной блокировки пользователя.
  6. *Video Circles*: компрессия в нативный 1:1 квадрат 360x360 (`LAYOUT_SCALE_TO_FIT_WITH_CROP`) на энкодере MediaCodec.
  7. *Admin Web*: защита порта 8081 с помощью Nginx HTTP Basic Auth.

## ADR-008: Архитектура удаления диалогов, тайпинг-маски видеокружков и управления фокусом ввода
- **Контекст**: Отсутствовала возможность удалить диалог (для себя или для всех), при записи видеокружка собеседник не видел соответствующий статус, выход из выделения сообщений самопроизвольно открывал клавиатуру, а панель эмодзи имела устаревшие иконки.
- **Решение**:
  1. *Soft / Hard Delete диалогов*: в `conversation_participants` добавлена колонка `cleared_at TIMESTAMP(6) NULL`. Удаление «для себя» ставит `cleared_at = NOW()`, отфильтровывая диалог в `ListConversations` и очищая локальную БД Room; при новом сообщении диалог восстанавливается с чистого листа. Удаление «для всех» каскадно удаляет запись из `conversations` и рассылает realtime WS событие `conversation_deleted`.
  2. *Маска записи видео*: событие тайпинга расширено полем `action` (`"typing"` / `"recording_video"`). При удерживании кнопки записи клиент шлет импульсы раз в 2 секунды, а UI получателя (в TopBar и в списке диалогов) показывает «записывает видео…».
  3. *Токены клавиатуры*: `MessageInputField` и `ChatScreen` отслеживают `lastHandledKeyboardToken` и `lastHandledComposerToken`, предотвращая автоматическое открытие клавиатуры при выходе из режима селекции сообщений.
  4. *Material Outlined иконки эмодзи*: в `FlowEmojiPanel` текстовые эмодзи в табах заменены на векторные Material Outline иконки с Telegram-подобным индикатором активной вкладки.

## ADR-009: Media-first архитектура чата для voice и Telegram-style альбомов
- **Решение (2026-09-11)**: сохраняем общий KMP/shared-контракт; voice message использует механику видеокружка (переключение одним тапом, удержание/отпускание, свайп-отмена и lock). Изображения отправляются Telegram-style альбомами до 5 элементов с одной общей подписью; выбор поддерживает галерею и камеру, редактор MVP — crop, rotate и draw. Выборки больше 5 изображений автоматически разбиваются на несколько альбомов. Видео, voice и изображения должны иметь durable outbox и переживать закрытие/перезапуск приложения.

## ADR-010: Реализация Media Foundation, Voice сообщений и Durable Outbox (Этап 1)
- **Контекст**: Видеокружки при сбоях сети или отсутствии S3 URL сбрасывались в текст `ChatMessageContent.Text`. Не было поддержки голосовых сообщений, waveform и надежного outbox для медиа.
- **Решение (2026-09-12)**:
  1. *Nested Media Contract*: унифицирован контракт сообщений на бэкенде и клиенте: `media` объект с полями `type`, `url`, `duration_ms`, `waveform`. Сохранена обратная совместимость с flat-полями (`video_circle_url`).
  2. *Durable Media Outbox*: `AndroidVideoCircleSyncCoordinator` адаптирован для очередей видео и войсов, состояние пишется в Room (`direct_chat_messages`), загрузка в S3 и отправка возобновляются после рестарта.
  3. *Voice Pipeline*: запись Ogg/Opus на API 29+ и AAC на API 28 (`VoiceRecorder`), расчет 48 точек waveform (0..100). Воспроизведение через ExoPlayer с seek по waveform и переключением скоростей (1x/1.5x/2x).
  4. *Управление жестами*: переключение Video/Voice по быстрому тапу, удержание для записи, свайп влево для отмены, свайп вверх для блокировки. Заблокированная запись формирует черновик в инпуте с возможностью прослушать перед отправкой.

## ADR-011: Реализация Telegram-style альбомов, Image Editor и Durable Outbox для изображений (Этап 2)
- **Контекст**: В чате требовалась отправка фотографий и альбомов до 5 штук с общей подписью, редактором фото, адаптивной сеткой со схлопыванием и интеграцией с корневым медиавьюером `FullscreenImageViewerV2`.
- **Решение (2026-09-12)**:
  1. *Группировка альбомов через `group_id` и `media_position`*: на бэкенде и в БД Room сообщения группируются по `group_id`. На клиенте `groupAlbumMessages` склеивает N сообщений в единый `ImageMessage` с списком `images: List<ChatImageItem>`, сохраняя порядок по `position`.
  2. *Динамическое схлопывание сетки*: при удалении любого сообщения из альбома оставшиеся элементы автоматически пересобираются по правилам сетки 1..5 фото без ломания верстки (с 5 в 4, с 4 в 3 и т.д.).
  3. *Telegram-style оверлей и подпись*: плашка со временем и статусом доставки рендерится поверх последней картинки с затемнением для читаемости на любых фото. Общая подпись (caption) от первого сообщения выводится под сеткой.
  4. *Attachment Picker & Editor*: шторка выбора с камерой (`FileProvider`) и недавними фото MediaStore. Встроенный редактор позволяет свободный кроп и пресеты (1:1, 4:3, 16:9), поворот на 90° и базовое рисование.
  5. *Durable Outbox*: `AndroidImageMessageSender` и `AndroidVideoCircleSyncCoordinator` сохраняют очередь отправки изображений в Room, гарантируя доставку при сбоях и перезапусках.

## ADR-012: Комплексное исправление и стабилизация медиа-сообщений (P0 Hardening & Streaming)
- **Контекст**: Аудит выявил критические P0-дефекты: блокировка `chat_image` на S3 presign, heap OOM при `file.readBytes()`, потеря медиа при рестарте приложения, конфликт тапа переключения режимов со стартом записи видеокружка, расхождение координат при рисовании в редакторе, отсутствие серверной валидации альбомов.
- **Решение (2026-09-12)**:
  1. *Allowlist S3 Presign*: `chat_image` добавлен в allowlist строк 226 `s3_presign.go` (`mediaKeyPrefix`, MIME types jpeg/png/webp, тесты `TestIsChatImageURLAllowedForUser`).
  2. *Durable Outbox & Recovery*: Room миграция 32 -> 33 добавила медиа-поля и `upload_stage` в `direct_chat_outbox_commands`. Стадии: `QUEUED`, `UPLOADING`, `UPLOADED`, `SENDING`, `SENT`, `FAILED`, `CANCELLED`. Файлы хранятся в `filesDir/chat_media_outbox/{clientMessageId}/` и физически удаляются только после серверного ACK (`markOutgoingSent`). При старте приложения незавершенные команды автоматически возобновляются.
  3. *Zero-OOM Streaming Upload*: `UploadsApiImpl` переведен на `OutgoingContent.WriteChannelContent` со стримингом блоками по 64 КБ без загрузки всего файла в heap.
  4. *Дедупликация и разделение жестов*: в `RecordingButtonGesture` тап (< 300 мс) переключает режим без старта камеры; запись стартует строго по истечении 300 мс. При выдаче разрешений сохраняется `pendingMediaAction`.
  5. *Серверная валидация альбомов*: бэкенд строго валидирует альбомы в транзакции: $0 \le \text{position} < 5$, совпадение conversation_id и sender_id, запрет коллизий позиций с поддержкой идемпотентного повтора по `client_message_id`.
## ADR-013: Устранение 4 дефектов медиа: отправка фото, слои редактора, удержание войса и деградация кружков
- **Контекст**: При физическом тестировании на устройстве обнаружены 4 бага: шторка фото закрывалась без отправки, редактор открывался под затемнением BottomSheet, запись войса срывалась через долю секунды, а видеокружки при перезаходе и входящие от собеседника деградировали в текст «Видеосообщение».
- **Решение (2026-09-12)**:
  1. *Отправка фото*: в `DirectChatStateHolder` добавлен кэш `localImageMessages` и методы обновления стейта; в `ChatRoute.sendImages` реализован безопасный fallback резолва `targetConversationId` через `getOrCreateDirectConversation`, отправка в `videoCircleSyncCoordinator.enqueueImage` и обработка событий успешной отправки и ошибок.
  2. *Полноэкранный редактор поверх всего*: в `ChatAttachmentPickerSheet` применен условный рендеринг: при `editingUri != null` вместо `ModalBottomSheet` рендерится `ChatImageEditorScreen`, исключая наложение слоев Window/BottomSheet.
  3. *Жест записи войса*: в `MessageInputField` удалено условие `&& !isVoiceRecording` из `showRecord`, что сохранило модификатор `Modifier.recordingButtonGesture` на кнопке и устранило срыв жеста при старте записи.
  4. *Защита видеокружков и войсов от сброса в текст*:
     - В `ChatsApiParsing.kt` парсер медиа сделан толерантным к отсутствию `objectKey`/`sizeBytes`.
     - В `DirectChatsLocalStoreImpl.upsertMergedMessage` защищены локальные пути `mediaLocalPath`, `contentType` и `mediaUrl` от затирания null.
     - В `AndroidChatThreadRepository.kt` и `AndroidChatRealtimeContract.kt` добавлено распознавание кружков и войсов по тексту «Видеосообщение»/«Голосовое сообщение» и `mimeType`, гарантируя правильный `ChatMessageContent`.
     - В `HasDataState.kt` исправлена видимость и расположение (`isOut`) для кружков и войсов.

## ADR-014: Стабилизация чата — контекстное меню фото, мгновенное превью, фоновый плеер войсов и атомарное удаление
- **Контекст (2026-09-12)**:
  1. При тапе на фотосообщение не открывалось контекстное меню (в отличие от текстовых), а тап по картинке не открывал вьюер.
  2. При отправке фото отсутствовало мгновенное превью для получателя и отправителя; требовалась оптимизация отправки и дизайна альбомов по образцу постов (скругления 12-16dp, gap 2dp, отмена отправки).
  3. Быстрое удаление сообщения и закрытие чата приводило к потере удаления, так как 5-секундный Undo-таймер отменялся в `disposeActiveWork()`.
  4. Голосовые сообщения прерывались при сворачивании приложения или выходе из чата из-за локального жизненного цикла ExoPlayer в Compose.
- **Решение**:
  1. *Жесты фото и альбомов*: разделены события тапа и лонгтапа в `ChatAlbumBubble`: тап по фотографии открывает полноэкранный вьюер (или переключает чекбокс в режиме селекции), лонгтап по фото или обычный тап по подписи/фону открывает контекстное меню чата.
  2. *Мгновенное превью и отмена загрузки*:
     - Клиент генерирует 32x32 stripped base64 JPEG микро-превью (`thumbnailUrl`) при компрессии (~300 байт), которое мгновенно передается в `media_thumbnail_url`. Получатель видит размытый превью с нулевой задержкой до полной выгрузки из S3 без создания нагрузки на CPU Go-бэкенда.
     - Добавлена кнопка отмены выгрузки (крестик на оверлее кругового индикатора прогресса) и повтора при ошибке.
     - Для предотвращения отзыва разрешений `content://` URI немедленно копируется в безопасный кэш приложения (`copyUriToSafeCacheFile`).
  3. *Надежное удаление сообщений*:
     - В `DirectChatStateHolder.disposeActiveWork()` добавлен принудительный коммит `flushPendingDeleteNow()`, исключающий потерю отложенного удаления при закрытии экрана.
     - В `ChatsRepositoryImpl.deleteMessage` локальное удаление из Room выполняется немедленно перед сетевым вызовом, предотвращая воскрешение сообщений при потере связи.
  4. *Фоновое воспроизведение войсов*:
     - Создан `FlowVoicePlaybackService` на базе AndroidX Media3 `MediaSessionService` с системным Media Notification (Play/Pause, закрытие, открытие чата по тапу).
     - Добавлены разрешения `FOREGROUND_SERVICE` и `FOREGROUND_SERVICE_MEDIA_PLAYBACK` для Android 14+.
     - `VoicePlayerManager` переведен в Koin синглтон с настройкой `AudioAttributes.CONTENT_TYPE_SPEECH` и фокусом аудио; из `ChatRoute` убрана принудительная пауза в `ON_STOP`, плеер продолжает играть в фоне.

## ADR-015: Детерминированные альбомы и ограниченный micro-thumbnail (13 сентября 2026)
- **Решение**: album identity на Android определяется только направлением `out/in` и стабильным `groupId`; лимит UI/client — 10 элементов, positions — `0..9`.
- **Решение**: micro-thumbnail остаётся client-generated JPEG data URI; Android ограничивает decoded thumbnail 8 KiB, Go валидирует prefix/размер до сохранения и рассылки.
- **Решение**: viewer origins привязаны к стабильному per-image key; remote URL имеет приоритет над local optimistic path после ACK.
- **Проверка**: targeted album regression test и Android compile прошли; backend Go tests и production smoke пока не подтверждены из-за отсутствия Go toolchain/устройства в текущем окружении.

## ADR-016: Chat-only sheet mechanics reuse (14 сентября 2026)
- **Решение**: chat picker получает profile-style `BottomSheetScaffold` mechanics локально в chat module; post creation screen и profile implementation не меняются.
- **Решение**: chat сохраняет собственный peek около 55%, но использует тот же принцип scroll handoff: scroll вверх раскрывает sheet, scroll вниз из top grid сворачивает, fling поддерживает collapse.
- **Решение**: горизонтальный selected-media preview добавлен только в chat picker; post composer остаётся источником визуального паттерна, а не изменяемой общей зависимостью.

## ADR-016: Единая капсула записи медиа (Voice & Video Circles) (13 сентября 2026)
- **Контекст**: ранее запись видео-кружков и голосовых сообщений жила на двух разных моделях данных и ветках верстки в `MessageInputField`. У голосовых сообщений не было визуальной пилюли замка при свайпе вверх, жесты лока не были согласованы, а отмена отображалась статичным текстом без анимации мусорки.
- **Решение**:
  1. В `core:uikit` создана единая модель `ChatMediaRecordingState` и компонент `UnifiedRecordingCapsule`.
  2. Пилюля замка (`RecordingLockPill`) вынесена в переиспользуемый компонент и активируется при свайпе вверх как для видео, так и для голосовых сообщений.
  3. Реализована живая анимация свайпа влево: при оттягивании пальца текст затухает, появляется иконка корзины с динамическим масштабированием и подсвечиванием красным цветом при достижении порога отмены.
  4. В залоченном состоянии отображаются: кнопка отмены (корзина) слева, таймер и эквалайзер по центру, кнопка паузы/стоп для голоса и круглая фиолетовая кнопка отправки справа.
  5. Микро-превью оптимизировано до 24x24 px Base64 data URI (~400 байт).
- **Проверка**: сборка `:core:uikit:compileDebugKotlin`, `:feature:chats:compileDebugKotlin`, `SharedChatUiAdaptersTest` и `:app:assembleProductionDebug` завершились успешно (код 0).

## ADR-017: Chat picker versus chat input media preview (14 сентября 2026)
- **Решение**: gallery picker не содержит selected-media strip; выбранные изображения живут в chat input до отправки.
- **Решение**: `ChatDraftImageStrip` переиспользует reorderable-механику post composer в chat UI без изменения post screen. Add-card снова открывает picker, reorder commit обновляет порядок draft URI.
- **Решение**: Attach button в picker всегда присутствует в нижней части sheet и disabled при пустом выборе.
- **Уточнение**: selected-media strip размещается отдельным sibling-слоем в `ChatScreenBody` над input, а не внутри `MessageInputField`; это фиксирует геометрию composer и предотвращает overlap.
- **Уточнение**: preview cards используют квадратный crop и Material theme tokens, чтобы одинаково работать в light/dark appearance.

## ADR-018: Оптимизация архитектуры Feed по результатам Ponytail-аудита (16 сентября 2026)
- **Контекст**: В модуле ленты скопились избыточные сущности: отдельный однофайловый модуль `:feature:feed`, дублирование логики парсинга ссылок/тегов между `SharedFeedScreen` и `PostScreen`, неиспользуемый кэш `feedCache` в `FeedApiImpl`, мертвые UI компоненты отладки и адаптер `SharedFeedPlatformUxAdapter`. При этом вертикальные свайпы ленты и их индикаторы требовалось строго сохранить.
- **Решение**:
  1. *Ликвидация модуля `:feature:feed`*: класс `FeedRoute.kt` перенесен в `:feature:shared/androidMain/kotlin/me/floow/shared/feed/ui/FeedRoute.kt`. Модуль `:feature:feed` удален из `settings.gradle.kts`, `app/build.gradle.kts` и файловой системы, снизив сложность сборки и оверхед Gradle.
  2. *Единый парсер ссылок `PostTextLinkify.kt`*: логика парсинга ссылок на посты (`https://floow.me/{user}/{id}`) и упоминаний (`@{user}`) объединена в `PostTextLinkify.kt`, используемом в `SharedFeedScreen` и `PostScreen`.
  3. *Удаление мертвого кода*: удалены `SharedFeedDebugComponents.kt`, `SharedFeedMediaContract.kt`, неиспользуемый `feedCache` в `FeedApiImpl`, адаптер `SharedFeedPlatformUxAdapter` и неиспользуемые методы управления рекомендациями в `SharedFeedModels`.
  4. *Инвариант*: жесты вертикальных свайпов (`onSwipeUp`, `onSwipeDown`, индикаторы и `SharedSwipeDirection.Up`) сохранены в неприкосновенности.

## ADR-019: Единая модель медиа FlowImageSource и оптимизация CPU микропревью (14 ноября 2026)
- **Контекст**: Размножение спаренных параметров `url` и `microThumb` по компонентам UI, расхождение политик мержа превьюшек в Room, передача `avatarThumb` через роутер и накладные расходы StackBlur.
- **Решение**:
  1. *Единая модель медиа*: `@Immutable data class FlowImageSource(val url: String?, val microThumb: String? = null)` в `:core:uikit`. Все UI компоненты принимают её как первичный параметр.
  2. *Единая политика мержа*: чистая функция `resolveMergedThumb` объединяет правила обновления и сохранения локальных кэшей для постов, аватарок и медиа.
  3. *Синхронное чтение из кэша (0 ms)*: `avatarThumb` исключен из аргументов навигации; `DirectChatsLocalStore.getCachedConversationSync` мгновенно отдает данные чата при монтировании экрана.
  4. *Оптимизация StackBlur & MicroThumbDecoder*: удален `coerceIn` из внутренних циклов фильтра, добавлен принудительный даунскейл до 24x24 перед блюром на Android/iOS, и сужен скоуп блокировки LRU-кэша.

## ADR-020: Telegram-parity stripped thumbnails (photoStrippedSize) (15 ноября 2026)
- **Контекст**: Передача полных JPEG-превью (~600–900 байт) в base64 data URI перегружала базу данных и сетевой трафик ленты и чатов. Попытки кодировать кастомные миниатюры приводили к невалидным маркерам в мобильных декодерах и мерцаниям (черные прямоугольники).
- **Решение**:
  1. *Бэкенд*: `internal/storage/minithumb.go` использует стандартный энкодер `image/jpeg` с качеством 20, вырезает заголовок и EOI-маркер и упаковывает чистые байты энтропийного скана в MTProto-подобный формат: `[0x01, height, width] + scanBytes`. Размер полезной нагрузки снижен до 50–70 байт (~70–110 символов base64 data URI).
  2. *Клиент (commonMain)*: `TelegramStrippedThumb.kt` держит статический 589-байтный заголовок стандартного baseline JPEG. Метод `inflate` на кадре 0 дополняет полезную нагрузку заголовком с подстановкой реальных размеров в SOF0 (байты 142 и 144) и завершающим EOI (`0xFF, 0xD9`). Нативные декодеры (Android `BitmapFactory`, iOS `Skia Image.makeFromEncoded`) получают 100% валидный JPEG без оверхеда.
  3. *Zero-flicker ProgressiveImage*: слой `microThumbBitmap` монтируется мгновенно на кадре 0, эмитит `onPainterChanged` для исключения скачков границ вьюера и плавно растворяется при загрузке целевой картинки (`targetAlpha == 1f`). При ошибке загрузки сети `InitialAvatar` чисто отображает инициалы.

## ADR-021: Стабилизация KMP DI, рантайма iOS и UI-аудит (16 ноября 2026)
- **Контекст**: При запуске общего Compose UI на iOS клиенте возникали рантайм-падения:
  1. `NoBeanDefFoundException` при открытии `SharedRepliesRoute` из-за безусловной привязки Android-only `NotificationsRealtimeRepository`.
  2. `IndexOutOfBoundsException` в фабрике `EditProfileStateHolder` из-за обращения к `params.get(index)`.
  3. `SIGABRT` / `NSInternalInconsistencyException` в `PlatformMediaRecorders.ios.kt` при отмене записи видеокружка до перехода `AVAssetWriter` в состояние `Writing`.
  4. При автоматизированном снятии UI для аудита (Twombly) лента захватывалась до завершения загрузки постов (черный экран 68 КБ), контекстное меню чата не удерживалось открытым, а фоновые раннеры `agent-device` и сборщики оставались висеть в памяти, потребляя 50–100% CPU.
- **Решение**:
  1. *Безопасный Koin DI в commonMain*: `SharedCommonModule.kt` переведен на `getOrNull<NotificationsRealtimeRepository>() ?: StaticRepliesRepository()`, исключив падения на iOS при сохранении нативной реализации на Android.
  2. *Типизированные параметры*: фабрика `EditProfileStateHolder` извлекает параметры через `filterIsInstance<...>()` вместо хрупкой позиционной индексации.
  3. *Гард AVAssetWriter*: в `PlatformMediaRecorders.ios.kt` вызов `finishWritingWithCompletionHandler` защищен проверкой `writer.status == AVAssetWriterStatusWriting`; во всех остальных случаях вызывается безопасный `cancelWriting()`.
  4. *Инварианты UI-скриншотов и Twombly*:
     - Запрещены слепые полные перезапуски сьюта (40+ экранов) при необходимости обновить 2–3 экрана: используется точечный пересъем и in-place обновление фреймов через `twombly update <frame_id> <path>`.
     - Скриншот ленты выполняется строго после ожидания маркеров загрузки постов (`0 комментариев`, `@y9finsi`) с паузой на отрисовку медиа Coil/Compose.
     - Оверлей контекстного меню сообщений проверяется на наличие экшенов в дереве перед снимком, а закрывается кликом по безопасному пустому фону `(50, 700)` без активации ввода.
     - Обязательный teardown: завершение процесса приложения `iosApp`, остановка демонов Gradle (`./gradlew --stop`), сброс блокировок SpringBoard раннера и шатдаун симулятора после завершения аудита.
