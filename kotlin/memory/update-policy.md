# Memory Update Policy — Регламент обновления памяти

Память полезна только тогда, когда она актуальна. Чтобы память не превращалась в кладбище устаревших заметок:

1. **Когда обновлять**:
   - При добавлении нового микросервиса, порта или базы данных -> `architecture.md`.
   - При изменении схемы авторизации, новых эндпоинтах API или миграциях -> `backend.md`.
   - При смене архитектурных слоев, DI или глобальных библиотек в мобилке/вебе -> `frontend.md`.
   - При обнаружении нового неочевидного бага, конфликта или серверного ограничения -> **немедленно в `gotchas.md`**.
   - При принятии важного решения (почему X, а не Y) -> `decisions.md`.

2. **Правила для агентов**:
   - Пиши коротко, емко, без воды и канцелярита.
   - Ссылайся на реальные пути файлов в репозитории.
   - Не дублируй то, что очевидно из `package.json` или `build.gradle.kts`.
   - **Лимит размера (Bloat Guard)**: Файлы активной памяти не должны превышать 30–35 КБ. Если раздел разрастается подробными логами спринта или пошаговыми фиксами багов, переноси их в `memory/archive/`, оставляя в основном файле только действующую архитектуру и правила.
   - **НИКАКОЙ «ЗАПИСИ ИЗ БУДУЩЕГО»**: Категорически запрещено писать в память о фичах как о «сделанных», если код ещё не написан или не собран/не проверен! Планы держи в плане, в память попадает только свершившийся факт.
   - После внесения изменений сообщай человеку: «Обновила память проекта в `memory/...`».
   - **НАПОМИНАНИЕ О НОВОМ ТРЕДЕ**: В конце ответа при завершении задачи агент обязан напомнить: «💡 Задача завершена, память зафиксирована — закрой этот тред и начни новый для следующей задачи, чтобы не забивать контекст!»
